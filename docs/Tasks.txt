BRINGING DB MIGRATIONS FORWARD TO NEWER BRANCHES
~~~~~~~~~~~~~~~~~~~~~~~~

Step 1: (ONCE ONLY) Configure .gitattributes to suppress snapshot conflicts
Add this to your .gitattributes so git never tries to auto-merge the snapshot:
*ModelSnapshot.cs merge=ours
This always keeps the current branch's snapshot during a merge, avoiding conflicts. The snapshot will be wrong after the merge, but you'll fix it with the script below.

Step 2: Merge the upstream (older) branch into the next-in-line (newer) branch, accepting the merge commit that git creates
e.g. BugFix -> Release (current) -> Pre-release -> Dev

Step 3: After the merge completes, explicitly take the upstream version of AppDbContextModelSnapshot.cs via PMC
Because .gitattributes with merge=ours auto-resolves the snapshot conflict without showing it in the VS conflict UI, the snapshot won't appear as a conflicted file for you to resolve — git will have already silently kept yours. You'll need to explicitly switch it to theirs after the merge completes, either via:

VS Git Changes panel — find AppDbContextModelSnapshot.cs in the changed files, right-click and choose Revert... then manually copy the file from the upstream branch, or
PMC which is more reliable:
git checkout HEAD^2 -- src/Constellation.Infrastructure/Persistence/ConstellationContext/Migrations/AppDbContextModelSnapshot.cs
The value of merge=ours in .gitattributes isn't that it resolves it the right way — it's that it prevents an unresolvable wall of merge conflict markers appearing in an already-complex generated file. You're trading an ugly conflict for a clean but wrong file, which you then deliberately correct in step 3.

Step 4: Add a new migration callsed _SnapshotRebuild, then delete the .cs and .Designer.cs files for this migration

Step 5: Push the updates for this branch, then move on to the new next-in-line branch to update
